# Наступні кроки

Навчальний план для самостійної роботи. Він продовжує дорожню карту з навчального блокнота
(етапи 1–4) з того місця, де робота зупинилася: інтерфейс `IRoomManager`.
У кожному кроці є **що зробити**, **підказки** і **як зрозуміти, що готово**. Готових рішень тут немає навмисно.

## Як працювати над кожним кроком

1. Створіть окрему гілку: `git switch -c feature/room-manager`
   (або в VS Code: клік по назві гілки в лівому нижньому куті → **Create new branch**).
2. Напишіть код і тести за схемою AAA та назвами `Метод_КолиУмова_ОчікуванийРезультат`.
   Корисно хоча б інколи писати тест **до** коду: спершу червоний, потім зелений.
3. `dotnet test` (або панель **Testing** у VS Code з C# Dev Kit): усе має бути зеленим.
4. Коміт і push: панель **Source Control** (Ctrl+Shift+G) або `git add`, `git commit`, `git push -u origin <гілка>`.
5. Pull Request: `gh pr create` або кнопка на GitHub → дочекайтеся зеленого CI (`gh pr checks`) → merge.

## Етап 1 (завершення). Доменне ядро

### Крок 1. Інтерфейс `IRoomManager` — тут ви зупинилися

**Що:** у `SyncWave.Core` створити папку `Interfaces` і файл `IRoomManager.cs` з контрактом, який ви обговорювали:
`CreateRoom(string roomCode)`, `GetRoom(string roomCode)`, `DeleteRoom(string roomCode)`, `GetAllRooms()`.

**Підказки:**
- Що повертає кожен метод? Подумайте, як `GetRoom` скаже «такої кімнати немає» і як `DeleteRoom` скаже «не було чого видаляти».
- Що має робити `CreateRoom`, якщо кімната з таким кодом уже існує?
- Чи мають коди `"Party"` і `"party"` вважатися однаковими? Це питання про формат `RoomCode`, яке досі відкрите.

**Готово, коли:** інтерфейс компілюється, і ви можете пояснити, чому кожен метод повертає саме такий тип.

### Крок 2. In-Memory реалізація `IRoomManager` + тести

**Підказки:**
- Яка колекція дає швидкий пошук за ключем (кодом кімнати)?
- В якому проєкті має жити реалізація? Згадайте план шарів: `Core` знає лише інтерфейси, а конкретні реалізації живуть у шарах вище.
  Поки немає `SyncWave.Infrastructure`, можна тимчасово тримати її в Core, але чесно це для себе позначте.
- Пізніше до менеджера одночасно звертатимуться кілька користувачів через SignalR. Звичайний `Dictionary` не потокобезпечний. Пошукайте, яка колекція в .NET розрахована на одночасний доступ.
- Тести: створити → знайти; знайти неіснуючу; видалити; створити дублікат.

**Готово, коли:** усі сценарії менеджера покриті тестами і зелені.

### Крок 3. Дублікати учасників

**Що:** зараз `Room.AddParticipant` дозволяє двічі додати учасника з тим самим `ConnectionId`.

**Підказки:**
- Що має статися з повтором: ігнорувати його чи кидати виняток? Досі в моделі ви використовували Guard Clause без винятків. Чи лишатися в цьому стилі?
- Пошук за `ConnectionId` у класі вже є. Де саме?

### Крок 4. Керувати відтворенням може лише хост

**Що:** за задумом хост ставить на паузу, перемикає треки, перемотує (і колись виганяє учасників), але зараз `Pause`, `Resume`, `SeekTo`, `PlayNext` не знають, хто їх викликає.

**Підказки:**
- Головне питання, яке досі відкрите: **де** перевіряти права? У самій `Room` (тоді методам треба знати, хто їх викликав) чи пізніше, у SignalR-хабі? Подумайте, що буде, якщо колись з'явиться другий вхід (REST), і перевірку там забудуть.
- Що відповісти гостю, який натиснув паузу: нічого, `false` чи виняток?
- Після зміни сигнатур старі тести перестануть компілюватися. Так і має бути: це нагадування оновити їх.

**Готово, коли:** є тести «хост може», «гість не може», «чужий не може».

## Етап 2. Стрімінг файлів

### Крок 5. Проєкти `SyncWave.Infrastructure` і `SyncWave.Web`

**Підказки:**
- Проєкти створюються командами `dotnet new` (шаблони: `classlib` для Infrastructure, `webapi` або `web` для Web).
  Потім `dotnet sln add ...` додає проєкт у рішення, а `dotnet add ... reference ...` створює посилання між проєктами.
  Те саме можна зробити через Solution Explorer у C# Dev Kit.
- Хто на кого посилається? Web → Core і Infrastructure; Infrastructure → Core; Core ні на кого. Чому саме так?
- Реєстрація `IRoomManager` у DI: який час життя потрібен сховищу кімнат у пам'яті — `Singleton`, `Scoped` чи `Transient`? Це питання було у ваших тестах у блокноті.

### Крок 6. Завантаження і віддача медіафайлів

**Підказки:**
- Завантаження: ендпоінт приймає файл (`IFormFile`). Перевірте розмір і розширення **до** збереження.
- Як назвати файл на диску? Чи можна довіряти імені, яке прислав браузер?
- Віддача: почитайте про HTTP Range Requests і параметр `enableRangeProcessing` у `Results.File` / `PhysicalFile`. Це дає перемотування без завантаження всього файлу в пам'ять.
- Коли видаляти файли? Наприклад, коли видаляється кімната (`DeleteRoom`). Це теж відкрите питання.

## Етап 3. Синхронізація

### Крок 7. SignalR-хаб і проста сторінка з плеєром

**Підказки:**
- `Participant.ConnectionId` уже заготовлений саме під SignalR.
- Групи SignalR добре лягають на кімнати: одна кімната — одна група.
- Події Play / Pause / Seek / AddTrack: хто їх надсилає, хто отримує?
- Сторінка: звичайний HTML + `<audio>` / `<video>` + JS-клієнт SignalR. Відкрийте дві вкладки й перевірте синхронність.
- Відкрите питання: як учасник, що зайшов посеред треку, дізнається точну позицію? Подумайте, чи не зберігати час останньої зміни стану.
